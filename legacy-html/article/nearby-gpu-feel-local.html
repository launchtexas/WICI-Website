Making a Nearby GPU Feel Local.

What has to cross the link when the GPU leaves the device.

TL;DR

  • A nearby GPU feels local only if the wireless link carries the right things. Making it as fast as PCIe is the wrong target.
  • What made the GPU feel local was never just moving bytes. PCIe hid thousands of small interactions between software and hardware. On a motherboard that chatter is cheap; over Wi-Fi it becomes the workload.
  • Generic RPC preserves the API shape but destroys the latency model. If every driver call becomes a wireless round trip, a fast GPU nearby can feel slower than a weak GPU inside the machine.
  • So WiCi keeps the local-GPU contract while shrinking what actually crosses the link: cache stable facts, deduplicate repeated payloads, compress or stream large transfers, pipeline independent work, keep expensive state resident, and preserve true dependencies exactly.
The GPU can leave the device only if the device still feels like the computer in charge.

The GPU has to leave, the experience cannot

A phone, tablet, headset, or small robot owns the live inputs: camera, microphone, touch, display, documents, notifications, identity, location, and sensor state. These are not peripherals around the workload. They are often the workload's source of truth. If an assistant is watching a screen, guiding a camera, responding to voice, editing video, or acting through a robot, the interaction loop begins and ends on the mobile device.

The compute that loop needs cannot live there. A flagship accelerator is built around hundreds of watts, dedicated cooling, and high-bandwidth memory — the wrong physical envelope for a device you hold in your hand. Cloud computing resolves that mismatch by moving the whole workload away, which works for batch and high-latency jobs but is a poor fit when the mobile device is not just a terminal but the host of the user's world. A nearby GPU box is the middle point: close enough to keep the interaction local, large enough to carry serious compute, and sharable enough to justify the hardware.

We covered why that shift is physically forced — the power, weight, and cooling budget a flagship GPU demands — in Move the GPU Out. Keep It Local. This post is about what happens once it does. The accelerator moves off the device, but the experience cannot follow it. The phone should never feel like it is calling a server; the app should never feel ported to a special endpoint. That is the challenge this post is about, and it is a protocol challenge before it is a hardware one. The question is precise: what must actually cross the link?

The misleading answer is "just call an API"

The obvious solution is to expose a high-level endpoint on the box: chat, image generation, transcription, embedding, or another task-specific route. This is a good product seam. It lets apps that already speak OpenAI-compatible or Ollama-compatible APIs use the box with little friction. WiCi uses that seam where it fits.

But it is not enough to make the GPU feel local.

Existing GPU software is not organized around a single remote endpoint. AI runtimes use CUDA, tensor libraries, memory allocators, graph capture, and model-specific kernels. Graphics applications use Vulkan, Direct3D, swapchains, fences, descriptor sets, and presentation paths. Video tools use encoders and frame buffers. Creative applications, game engines, robotics stacks, and local agents all assume the accelerator appears through the normal device stack.

If every app must be rewritten against a WiCi-specific API, the nearby GPU becomes another cloud service with a shorter cable. It may be useful, but it does not preserve locality. The stronger goal is compatibility: unmodified or minimally changed software should continue to see a GPU-shaped system.

That goal pushes the protocol down a layer. The question becomes: can a wireless link carry the job that PCIe used to perform?

PCIe is not just bandwidth

It is tempting to compare links by peak throughput. PCIe 5.0 operates at 32.0 GT/s per lane; an x16 link is roughly 64 GB/s in each direction. Wi-Fi is a shared packet network whose real application throughput depends on spectrum, channel width, interference, distance, retries, access point quality, and other clients.

The bandwidth gap matters. But bandwidth is not the deepest problem. The deeper problem is latency and dependency structure. A local driver interface is fine-grained because the bus is assumed to be near. Programs query device attributes, allocate memory, copy buffers, launch kernels, wait on fences, check status, create objects, bind memory, and read results. On PCIe, many of these calls are cheap enough to hide under compute. Across Wi-Fi, each one can become a round trip.

The cost is not one big tensor crossing a slower link. The cost is query, wait; create, wait; copy, wait; submit, wait; present, wait; read status, wait. At that boundary, latency is no longer around the workload. It becomes part of the workload.

This is measurable, and the size of it surprised us. Running the trivial nvidia-smi status command locally finishes in 51 milliseconds. Hijacking the same command at the kernel driver and forwarding each call to a GPU one Wi-Fi hop away made it 51× slower, because that one command turns into nearly 800 round trips. A real workload is worse: a single image-understanding inference (a Qwen-VL-8B model, ~180 output tokens) issues roughly 20,000 user-mode driver calls. Naively remoted, those calls alone stretch a sub-two-second job past 20× its local time.

This is why a naive remote driver can lose even when the GPU is much faster than the local machine. The accelerator may finish the compute quickly, but the application is stalled by serialized network dependencies. A powerful GPU on the other side of a bad protocol behaves like a fast engine attached to a gearbox made of stop signs — and the stop signs dominate: at the median, a single remote function call takes 483× longer than the same call executed locally (97× even at the 90th percentile). The base round-trip time of the wireless link, not bandwidth, is what sets that gap.

Generic RPC is the wrong layer

The first implementation mistake is to treat every driver call as a generic function call: serialize the name, serialize the arguments, send over TCP, execute remotely, and return the result. This is easy to reason about and hard to make fast. It preserves correctness by making every call synchronous. It also preserves the worst possible latency model.

The protocol only starts to improve when it understands the semantics of the GPU API. Not all calls are equal.

The time to remote a job has a simple shape. If a task takes Tlocal on the GPU itself, doing it over Wi-Fi costs TWiCi = Tlocal + N·RTT + D/Rate: the compute, plus one round trip for every one of the N driver calls that has to block, plus the time to move D bytes at the link rate. Bandwidth lives in the last term; the middle term is the one that explodes. The crossover is just algebra: a fast remote GPU loses to a weak local one whenever N·RTT grows larger than the local compute it was supposed to save. At N = 20,000 calls and a 1.5 ms RTT, that middle term alone is 30 seconds — for a job that runs locally in under two. So the protocol's real job is to shrink N.

So the real problem is one of judgment, not speed: tell apart the round trips that are genuine dependencies from the ones that are not, preserve the first exactly, and spare the second — all without asking the application to change. Most of the chatter turns out to be the second kind. A great deal of it is repeated, predictable, or waiting on no one; only a thin slice is a true dependency where the next step genuinely needs the last one's result. Get that judgment wrong on the thin slice and the answer is not merely slow, it is incorrect. Get it right and most of the link goes quiet.

Why prior GPU remoting does not transfer

Remoting a GPU API is not a new idea. rCUDA, sCUDA, ZLUDA, and KRYPTON all intercept at the CUDA or kernel-driver level and ship calls to another machine; GaiaGPU, qCUDA, and vCUDA virtualize GPUs to share or cap them among tenants. The interception point WiCi uses is borrowed from this line of work.

What does not transfer is the assumption underneath it. Those systems were built for the datacenter: a stable, high-bandwidth, wired interconnect at microsecond latency, where leaving a call synchronous costs almost nothing. The nearby-GPU regime is the opposite — Wi-Fi delivers millisecond RTTs against PCIe's microseconds, around 1 Gbps against tens of Gbps, and adds stochastic jitter from contention and retries. Run an unmodified datacenter remoting stack over that link and it degrades exactly as the round-trip math predicts, because it has no machinery to hide latency it was never designed to face. The hard part is not where you intercept the GPU; it is the latency-hiding you add on top, so that interception point can survive a wireless link.

A nearby GPU needs four protocol layers

The public mental model is "GPU over Wi-Fi." The systems model is more specific. To make the nearby GPU feel local, WiCi needs four layers working together.

1. Compatibility layer

The application should see the interface it already expects: a GPU adapter, a CUDA-like compute path, a Vulkan or graphics path, an encoder path, or a familiar model endpoint. This does not mean every API must be complete on day one. It means the protocol starts from the app's existing contract rather than inventing a new one and asking the ecosystem to port upward.

2. Semantic transport layer

The transport should know when it is carrying a query, a command, a memory update, a synchronization point, or a present operation. That knowledge lets it choose between synchronous calls, asynchronous commands, pushed results, cached replies, compressed payloads, and local status resolution.

3. Residency layer

PCIe-attached GPUs are usually owned by one host. A nearby GPU box is naturally shared: a phone may run an agent, a laptop may render, a local memory service may keep embeddings or model weights warm, and a background app may ask for short bursts.

The protocol therefore needs a memory system, not just a wire format. Large allocations should stay logically stable. Model weights and other expensive state should remain resident when possible. When memory pressure forces eviction, the system should evict and restore state without invalidating the handles and pointers already embedded in work.

4. Network-control layer

Wi-Fi is not a backplane. It is shared, bursty, and environmental. A protocol that works only on average latency will stutter on tail latency. That pushes WiCi toward controlling more of the local path: discovery, pairing, access point placement, link selection, queueing, and eventually hardware co-design.

The useful analogy is not cloud gaming

Cloud gaming renders the whole application remotely and streams video back. That is a strong architecture for some games. It is the wrong analogy for general nearby GPU use.

In many WiCi workloads, the mobile device remains the host of the experience. It may own the camera frame before inference, the touch event before rendering, the file being edited before encoding, or the robot state before the next action. Streaming a remote desktop back to the device is too blunt. It moves the application away from the place where the user's state lives.

WiCi is closer to moving the device boundary than moving the application. The application should remain attached to the user's device while selected GPU work executes nearby. That distinction is why the protocol cares about driver semantics, object handles, memory state, fences, dirty ranges, and pushed frames. These are the details cloud streaming usually hides by relocating the whole session.

What we learned at the boundary

Compatibility has to be won below the app. A high-level API is valuable, but it cannot carry the whole ecosystem. The apps that make local GPUs valuable are often the least likely to rewrite themselves for a new endpoint: renderers, editors, runtimes, game engines, robotics libraries, and model stacks.

The enemy is serialized waiting. Bandwidth improvements help large transfers, but the sharpest wins come from removing unnecessary synchronization: cache invariant queries, push timeline updates, send independent work asynchronously, track dirty memory rather than copying everything, and return frames or results on streams that do not block command submission.

Residency is a first-class protocol concern. A nearby GPU box serves bursts from multiple devices and applications. If every burst reloads the world, the user feels the box as remote. If the system keeps the right state warm, the same physical link feels much closer. Scheduling and memory management are part of the protocol, not implementation details underneath it.

These lessons are not specific to one graphics API or one model runtime. They apply whenever software built for a local device fabric is moved onto a network.

What we are not claiming

We are not claiming Wi-Fi becomes PCIe. It does not. PCIe is a high-speed, low-latency device interconnect. Wi-Fi is a shared wireless packet network.

We are not claiming every GPU workload should be remote. Some workloads are too latency-sensitive, too bandwidth-heavy, too synchronized, or too dependent on unsupported driver features. Workloads dominated by large uploads and tight result readbacks, in particular, leave the protocol little to save — the data and the unavoidable dependencies swamp it. The protocol should expose those limits rather than hide them.

We are not claiming average latency is enough. Interactive systems fail at the tail. A convincing WiCi system has to measure jitter, contention, cold starts, multi-client interference, and state restoration, not just a happy-path demo.

We are not claiming a single abstraction wins. Model APIs, app-side SDKs, driver-level remoting, local execution, and box-hosted services all have roles. The research question is how to route work to the lowest layer that preserves both compatibility and performance.

Why this matters for personal AI

Personal AI is not just a chatbot that follows you around. It is a stack of live loops: voice, vision, memory, action, and adaptation. These loops are naturally mobile because the user's world is mobile. They are also increasingly GPU-heavy. That tension is the reason WiCi exists.

If the GPU must stay in a box, the box has to disappear from the experience. The phone should not feel like it is calling a server. The app should not feel ported to a special endpoint. The user should not think about where the model, renderer, encoder, or memory engine lives. The protocol should make the nearby accelerator look like part of the local machine.

That is the standard PCIe quietly set inside the workstation. WiCi's protocol work asks how much of that standard can be preserved after the wire becomes wireless.
