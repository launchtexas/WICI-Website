The GPU Never Learned to Share.

CPUs have scheduled cycles for sixty years. GPUs are only now learning to schedule VRAM.

TL;DR

  • For most of their history, GPUs assumed a single dominant tenant: one game, one render job, one training run. That assumption held because, for decades, it mostly matched reality.
  • Local AI breaks it. One machine can now run several independent model processes side by side, an always-on AI-native OS layer, and the traditional mix of gaming, streaming, and creative tools — all reaching for the same chip at once.
  • CPUs schedule cycles. GPUs must schedule VRAM. A CPU's schedulable resource is renewable and nearly free to hand off: save a register file, move on, microseconds. A GPU's schedulable resource in AI workloads is multi-gigabyte resident state that cannot be paused for free. That difference is why GPU scheduling still lags CPU scheduling by decades.
  • Datacenter answers exist — MIG, MPS, time-slicing — but each trades flexibility for isolation, none of them reach consumer silicon, and the software ones still cost real throughput the moment more than one workload actually contends for the chip.
  • We think the fix has to schedule at a different unit than a page or a process — something closer to the individual memory allocation. This post is about making the problem precise; the mechanism is its own post.
CPUs learned to share sixty years ago. GPUs are only now being asked to.

One pipeline, one owner

For most of computing history, a GPU had exactly one job. Graphics processors began as fixed-function pipelines built to accelerate a single rendering task for a single running application: one game, one 3D scene, one frame at a time. Even after GPUs became programmable, general-purpose compute engines, most systems kept scheduling kernels from one application at a time; only once GPUs moved into datacenter and virtualization settings did researchers begin retrofitting the time- and space-multiplexing techniques CPUs had used for decades onto GPU hardware.

CPUs had solved the identical underutilization problem decades earlier, and they solved it with an architecture change, not a workaround. Batch-processing computers of the 1950s sat idle waiting on a tape drive or a printer while a program blocked on I/O. Multiprogramming fixed the easy version of that problem by keeping several programs resident in memory, so the operating system could switch to another the instant one stalled. By the 1960s the idea had matured into true time-sharing: MIT's Compatible Time-Sharing System, John McCarthy's 1959 memo arguing that shared, interactive computing would multiply programmer productivity, and the Multics project that followed it — a name literally short for "Multiplexed Information and Computing Service." A computer with one processor could feel, to every person logged into it, like their own.

GPUs never needed that trick, for a simple reason: they had no tenants to share among. A gaming GPU ran one game. A workstation GPU rendered one scene. A training GPU ran one job to convergence. Scheduling among tenants is only a hard problem once tenants exist and compete for the same chip, and for almost the entire history of the GPU, they didn't.

The homogeneous era is ending

That condition is ending from three directions at once, and none of them is hypothetical.

Many independent AI processes, one machine

Local and edge LLM deployment is now a deliberate architecture choice, not a fallback. A 2024 Linux Foundation survey found that 38% of organizations already self-host generative-AI models on premises, and 16% run them locally on edge or end-user devices, citing data control, cost, sovereignty, and latency as the drivers. That local serving is already visible at internet scale: a Shodan-based scan by Cisco Talos found 1,139 exposed Ollama instances, 214 of them actively hosting live models. Ollama's own serving policy assumes concurrency is normal, defaulting to three loaded models at once on a GPU host.

On one developer machine, that concurrency looks like an editor assistant, a command-line coding agent, a notebook kernel, and a chat UI, launched independently, each keeping its own process, lifetime, and CUDA context, and often loading the same base model into separate memory. Three or four tools, each reasonable on its own, add up to a GPU working-set problem no one of them created.

An AI-native OS layer that never turns off

Personal AI is also moving into the operating system itself. At Build 2026, Microsoft described Windows AI Foundry as a routing layer that selects models across NPU, GPU, and CPU depending on what a task needs and what's available. Local AI on the GPU is also no longer gated behind Copilot+ NPU hardware: as of June 2026, Windows 11's local Language Model APIs run on any NVIDIA GeForce RTX 30-series-or-newer GPU with at least 6 GB of VRAM, not just NPU-equipped Copilot+ PCs. A background OS feature that indexes, summarizes, or captions your activity now competes for the same GPU as whatever you're actually running.

The traditional mix hasn't gone anywhere

Meanwhile the workload GPUs were already juggling hasn't disappeared. Windows has managed multiple simultaneous GPU consumers — games, browsers, video capture, overlays, desktop composition — ever since Hardware-Accelerated GPU Scheduling moved scheduling decisions off a dedicated CPU thread and onto the GPU itself. Add a local model to that mix and the contention stops being latent: you can run a big local model or a demanding game on a consumer GPU, but rarely both at once, because both are drawing from the same fixed pool of VRAM.

None of these three is new by itself. What's new is that they now land on the same consumer GPU, at the same time, on hardware that was never designed to referee between them.

Cycles vs. VRAM

The resource that breaks the analogy.

It is tempting to treat this as a solved problem wearing a new hat: CPUs figured out scheduling in the 1960s, so give the GPU a scheduler and move on. That undersells what actually made CPU time-sharing cheap, and it is worth being precise about what a scheduler is multiplexing in each case.

A CPU scheduler multiplexes cycles: time on a core. Cycles are renewable — the next one is always coming — and handing them to a different tenant is nearly free. A context switch saves a register file and a small amount of kernel state, on the order of microseconds. Because the resource itself costs almost nothing to hand off, an OS can switch tenants dozens of times per second and every user feels like the machine is theirs alone.

A GPU scheduler, for AI workloads, has to multiplex something else: VRAM. Model weights, KV-cache, and workspace state for a modern local model are gigabytes of resident, load-bearing memory, and unlike a register file, most of it cannot be reconstructed for free. Moving it means real bytes crossing a real bus, and evicting it before serving the next tenant means the previous tenant has to be restored before it can run again. GPU context switching does not inherit the "basically free" property that made CPU time-sharing painless — it is a different problem wearing the same name.

The industry has already tried to close that gap in the datacenter, and the results show the tradeoff rather than hide it. NVIDIA's Multi-Instance GPU statically partitions a chip into hardware-isolated slices with near-zero scheduling overhead, because isolation is enforced in silicon rather than decided by a scheduler — but the partitions are fixed-size, so a workload that doesn't match a profile wastes whatever doesn't fit. Time-slicing keeps the whole chip flexible instead, letting a software scheduler rotate through workloads on one physical GPU, but that flexibility costs real throughput once multiple workloads genuinely contend for the chip, with the overhead worsening as more workloads try to share it at once. Neither answer reaches a consumer GPU at all; MIG and enterprise time-slicing are datacenter-tier features.

Buying more VRAM doesn't dissolve the problem either, because VRAM is the most expensive place to leave a byte at rest: GPU memory runs well over an order of magnitude more per gigabyte than DDR5 system memory, and roughly two orders of magnitude above PCIe 5 NVMe storage, which is exactly why serious systems keep a memory hierarchy instead of treating VRAM as infinite. That gap is compounding on the consumer side right now: memory fabs have shifted GDDR production capacity toward HBM for datacenter accelerators, and Nvidia is reportedly cutting consumer GPU supply by 30–40% through early 2026 as a result. The scarce resource is not getting less scarce.

Why this is hard

Granting that VRAM, not cycles, is what a GPU scheduler has to move, the engineering problem breaks into four distinct difficulties.

Classification is a one-sided proof problem. CUDA's allocation and copy APIs expose addresses, sizes, and streams — not what the bytes inside an allocation mean. Deciding that a large allocation is an immutable model weight, and therefore safe to share across processes, has to be right every time: a false positive can share a private prompt or a live KV-cache and corrupt another process's data, while a false negative only costs some memory. That asymmetry means classification has to work like a positive proof rather than a best guess, and it has to run without slowing down the token-generation path it exists to protect.

Moving memory at line rate is a different problem from moving it at all. A model's resident state is scattered across many separate allocations, but fast storage only approaches its rated bandwidth with large, aligned, asynchronous requests at deep queue depth. A naive mechanism that simply copies each allocation as it finds it turns eviction into thousands of small, serialized transfers — the movement becomes part of the request's critical path instead of hiding behind a background flush.

The cost of serving one request depends on what you served last. Unlike a CPU scheduler's roughly fixed time slice, a GPU residency decision is stateful: serving one client can leave a model resident and cheap for the next request, or force a different client's private state into a slow restore, or evict a group before its state is safely saved. FCFS and LRU-style policies don't see any of that; they know when something was last touched, not what it will cost to make the next thing runnable.

Sharing physical memory across processes without merging their execution is its own protocol problem. The obvious shortcut — make every local tool join one shared serving runtime — doesn't fit local tools that need their own lifetimes, plugins, and execution contexts. The primitives that let one process hand physical memory to another exist, but they don't come with the layer on top of that: verification that shared bytes are genuinely immutable, an ownership protocol between the first process to load something and every later one, and a safe fallback when detection fails.

Existing tools each pick a control granularity, and each one is wrong for local AI in the same direction: too coarse, or too blind, to tell a duplicated model weight apart from the private state sitting right next to it. Page-level memory management increases apparent capacity but throws away the information that a given page belongs to an immutable weight tensor shared by three processes rather than a private buffer belonging to one of them. Whole-process checkpointing goes the other way: it recovers memory by suspending an entire application, which is powerful for coarse-grained recovery but moves far more state than the one duplicated object that actually caused the pressure. Serving frameworks that pool requests behind one shared runtime solve sharing cleanly, but only for callers willing to give up their own process and execution path — a fine trade for a hosted service, a bad one for an editor plugin or a CLI tool that needs to keep running as itself. The unit that's actually missing sits between a page and a process: something closer to the individual large memory allocation, big enough to be the thing causing pressure, small enough to leave everything else about the client process untouched.

Why this matters for WiCi

We've written before about why the flagship GPU a personal AI system needs has to leave the mobile device (Move the GPU Out. Keep It Local.) and about what has to happen to the protocol so that GPU still feels local once it does (Making a Nearby GPU Feel Local). This post is about what happens once it's there: a nearby GPU box is not one user's dedicated accelerator. It's shared — a phone's agent, a laptop's renderer, a background memory service, and whatever the OS itself is quietly running, all reaching for the same chip. That's a scheduling problem before it's anything else, and it's the same problem CPUs solved sixty years ago, for a resource that behaves nothing like a CPU's.

This is the layer we're building at WiCi: a scheduler that treats VRAM as the thing being multiplexed, not an afterthought sitting underneath a scheduler built for cycles. The mechanism — how we classify, move, and schedule that memory — is its own post. What matters here is getting the problem statement right first: any system that puts one GPU behind more than one independent, live client — a shared workstation, an edge box, a nearby accelerator serving a phone and a laptop at once — is going to hit the same wall CPUs hit in the 1950s: a scarce resource, several tenants, and no scheduler that understands what it's actually moving. GPUs are only now being asked to share. Getting the resource model right — VRAM, not cycles — is the difference between a scheduler that works and one that just adds latency to look busy.
