Some large open-weight models require more memory than a consumer computer provides. DeepSeek-V4.1-Flash-1017 and Muse-Spark-Open are 763B- and 816B-class releases. Their weights occupy hundreds of gigabytes even in the formats used for local inference. A laptop or a desktop GPU holds a fraction of that in memory.

InferSSD keeps routed expert weights on NVMe storage and reads the working set selected by the model during inference. Attention, shared computation and the dynamic KV cache remain in RAM or VRAM.

InferSSD is an open-source inference runtime built on llama.cpp. It retains GGUF files, browser chat and an OpenAI-compatible API, with an explicit path for expert indexing, I/O, caching and execution. It follows the argument of The SSD Is the New VRAM and the joint SGLang SSD Expert Pack work. This article describes that design and the current recorded results on Apple Silicon and NVIDIA systems.

What runs on consumer hardware

On an RTX 5090 with 32 GB of system RAM and 32 GB of VRAM, InferSSD processes the DeepSeek 4K prompt tier at 164.5 tokens/s and generates at 7.27 tokens/s. On a 48 GB M5 Max MacBook Pro, the current summary reports 26.270 tokens/s prefill and 2.704 tokens/s decode. The RTX 5060 Ti system, with 8 GB system RAM and a separate 16 GB of VRAM, reaches 75.1 and 2.55 tokens/s.

The following tables use the current README benchmark snapshot. Prefill is prompt-processing throughput. Decode is measured over tokens 129–256 of a 256-token output. The 4K label describes the input tier; actual token counts depend on the chat template.

Hardware configuration

The benchmarked MacBook Pro has a 2 TB internal SSD and 48 GB unified memory. The two RTX systems use 2 TB ZHITAI TiPro9000 drives, connected over PCIe 4.0 ×4 on the 5060 Ti system and PCIe 5.0 ×4 on the 5090 system. DGX Spark has 128 GB unified memory and a 4 TB Samsung SSD. CPU, memory, drive, connection and cache budget all influence the result. The product page includes the full hardware table.

Scope of the comparisons

The measurements report throughput for complete inference configurations. Different backends, weight formats, batching, caches and generated continuations prevent attributing the difference to any single optimization.

On Mac DeepSeek, the GGUF engines use Metal with CPU routed experts, while the tested Colibri configuration uses the CPU and the official Safetensors checkpoint. On Mac Muse, the llama.cpp baseline uses a different template and input length. Linux numbers are tester-reported summaries. The methodology distinguishes current summaries from historical run artifacts; older timing logs are not evidence for a newer summary value.

The 5090 DeepSeek rates correspond to 20.41× prefill and 8.39× decode relative to the recorded llama.cpp rates on that system. Those ratios apply to that model, machine and test configuration. Model loading, source preparation and the first launch’s hardware profiling are separate from serving throughput.

SSD storage for routed expert weights

NVMe storage provides capacity for models that exceed a machine’s memory, but its bandwidth is lower than RAM and NAND flash has a finite program/erase budget. The access pattern determines how useful that capacity can be.

Static weights and dynamic KV caches

The KV cache stores state produced while processing a conversation and grows as tokens are added. Offloading that changing state to SSD can introduce substantial writes. Gandalf [1], a study of SSD-backed KV caching, examines this endurance problem and uses application-aware cache admission to reduce writes. InferSSD’s expert-weight path addresses a different workload: reading model parameters that stay fixed throughout inference.

A mixture-of-experts model routes each token to a subset of its experts. The total expert set can be much larger than the set needed for one computation. InferSSD uses this distinction to separate model capacity from working memory.

The expert weights are static during inference. After setup, the expert path reads selected byte ranges and reuses cached weights. Prompt batching spreads a weight read across tokens that choose the same expert. A cache hit avoids another SSD read, and execution can use the processor where the weights are already available.

Shared layers, attention and the active KV cache still need working memory. The memory budget must cover these allocations as well as temporary activations and expert buffers. Keeping expert weights on SSD removes the requirement to hold the whole expert set in RAM or VRAM; the rest of the inference workload must still fit.

This requires careful management of a limited bandwidth budget. Storage capacity alone does not determine token speed: the amount actually fetched, cache reuse, batch shape, CPU computation and transfers to GPU memory all matter.

Checkpoint formats

The DeepSeek release’s 763B label describes its published checkpoint. The recorded text GGUF contains 748.49B parameters and omits vision and MTP/DSpark modules. Its Q8_0 label covers a mixture of tensor formats: routed experts retain MXFP4, while other tensors include Q8_0, BF16 and F32. Muse uses the Unsloth UD-Q4_K_XL GGUF conversion.

Expert packing copies the existing quantized expert payload without further quantization. That does not make a text GGUF identical to the full published checkpoint, or establish equal output quality across different formats. The model references and conversion details are part of the benchmark definition.

The expert inference pipeline

With memory-mapped weights, accessing a page that is absent from RAM can make computation wait while the operating system fetches it from storage. A general-purpose page cache has limited knowledge of which expert matrices the next operation will need.

InferSSD explicitly connects expert indexing, token grouping, caching, reads and execution. The router selects experts; the runtime checks their residency, reads missing weights and schedules computation under a shared memory budget. These five mechanisms determine how many bytes move and when the processors can use them.

1. Address the expert bytes directly

A source index locates each expert’s up, gate and down matrices in the original GGUF shards or a matching expert pack. This gives the reader byte ranges for the selected expert without loading the surrounding experts. Indexing GGUF headers avoids copying the weight payload. Packs arrange expert slices by layer and expert with 4 KiB alignment while preserving their quantized bytes.

The current launcher can prepare a direct GGUF alias index, so a separate pack is optional. The benchmarked DeepSeek GGUF occupies about 473 GiB; an optional pack adds about 269 GiB. Each pack must stay paired with the source checkpoint: the v1 format has no checkpoint fingerprint.

2. Share weight access during prefill

The model router selects experts for each token at each layer. During prefill, many tokens can select the same expert. Grouping these tokens lets one weight read serve multiple matrix multiplications. A longer prompt creates more opportunities for this reuse.

Larger batches also consume more temporary activation memory, so batch size and expert-cache capacity compete for the same budget. Reclaiming cache space can make room for prefill work; decode then has a different balance between batch size and keeping frequently used weights resident.

The launcher chooses machine-dependent settings and allows explicit batch and micro-batch limits. Linux additionally exposes an online controller through the Python API. macOS uses static launch settings. These platform differences matter when interpreting prefill results.

An earlier fixed-batch Linux experiment illustrates the tradeoff: on a 436-token prompt, with a 24 GiB host-memory limit and a 7 GB/s host-to-device budget, increasing the batch size from 64 to 128 reduced reported prompt SSD reads from 465.1 GB to 314.5 GB and increased prefill throughput by 47.5%. This development experiment is separate from the current 4K benchmark tables above.

3. Keep reused experts in a bounded cache

Token grouping shares reads within a batch. Caching extends reuse across batches and generated tokens. Before requesting weights from the SSD, the runtime checks whether they are already resident. A hit saves another read.

InferSSD accounts for host-memory use and provides an expert cache under the configured budget. On Linux with CUDA, a GPU cache tier can keep selected expert weights in VRAM. Active weights must remain available until their computation finishes; cache hit, miss and eviction counters help explain how a particular memory budget behaves.

The runtime also needs memory for attention, the KV cache, activations and backend work buffers. Cache capacity can be reclaimed to make room for other allocations. A useful configuration balances reuse against the memory needed to execute the next operation.

4. Stream cache misses in compute order

Explicit readers submit expert reads into buffers managed by the runtime. The current architecture uses io_uring on Linux and persistent reader threads with F_NOCACHE on macOS. This lets the engine coordinate I/O and memory accounting around the expert workload.

The Linux direct-I/O path uses O_DIRECT to bypass the file page cache. Read scheduling also follows dependencies within an expert: up and gate matrices produce an intermediate activation, and the down matrix consumes it. Prioritizing up and gate allows their computation to overlap with reading the down matrix. Useful overlap depends on the reader, storage device and execution configuration.

5. Choose the execution backend

Moving expert matrices over PCIe costs time. Reusing weights on the GPU can pay off for grouped prompt work, while CPU execution can avoid an upload for weights already in host memory. The runtime’s placement logic considers measured costs and residency.

During discrete-GPU decode, an expert already in VRAM can run on the GPU while the CPU processes experts resident in host memory. This exchanges small activation vectors between processors instead of uploading every weight matrix for each generated token. Supported CUDA systems with coherent memory, such as DGX Spark’s GB10, can also read host expert buffers through host page tables.

On Apple Silicon, Metal handles dense computation and the CPU sink computes routed experts. Linux/CUDA adds a GPU expert-cache tier. The same high-level data flow therefore maps to different execution paths on the two platforms. The architecture guide documents the modules and ownership boundaries.

SSD endurance and read disturb

Expert weights and dynamic inference state have different access patterns. InferSSD’s expert path reads static model weights; attention and the dynamic KV cache stay in working memory. Expert-cache replacement happens in RAM or VRAM.

SSD endurance ratings commonly use terabytes written (TBW), reflecting the finite program/erase budget of NAND flash. Downloading weights and preparing an optional pack write data during setup. Reading those files during inference does not add the same volume to the host-write total. Operating-system swap, logs and other system activity can still generate writes, so memory pressure and actual device I/O matter.

What happens inside the drive

Repeated NAND reads can disturb neighboring cells and increase errors. Firmware can refresh affected data by correcting and rewriting it to another location. These internal writes consume part of the program/erase budget and can affect read latency, even during a host workload that only reads. DEAR [2] and the read-latency relaxation study [3] examine this behavior.

A conditional wear-budget model

We used the DGX Spark / DeepSeek 4K-input, 256-token-output test logs to explore an intensive daily-use scenario: eight hours of use at a 50% active-inference duty cycle, equivalent to four hours of continuous reading. Extrapolating that workload gives roughly 85 TB of host reads per day. This is an estimate that uses engine expert-copy volume during prefill as a proxy for device reads; it is not a measured daily block-device total.

A simple refresh-only wear-budget estimate is:

Years ≈ (Capacity × Remaining P/E cycles) / (365 × Daily read volume × R)

Capacity and daily read volume use the same unit, such as TB. R is internal refresh bytes written divided by host bytes read. Remaining P/E cycles are an assumed budget, not a measurement of a particular retail drive. The model assumes uniform wear leveling and omits over-provisioning differences and writes from other workloads.

In DEAR’s experiments [2], two TLC samples and one QLC sample produced approximately 0.9, 2.4 and 8.2 TiB of internal refresh writes after 30 TiB of reads. Dividing these values gives illustrative ratios of 3%, 8% and 27.3%. The tests used specific SATA SSDs and 4 KiB random reads. InferSSD uses much larger, aligned matrix reads on NVMe storage, so those ratios cannot be treated as constants for its drives.

Within this model, halving active read time halves the estimated daily read volume and doubles the calculated wear-budget duration. A drive’s actual refresh policy, prior wear, temperature and workload can change the result. Field reliability research [4] also shows that failures depend on interacting factors beyond a single wear measure. These calculations describe assumptions to test, rather than a promised drive lifespan.

For sustained use, size the SSD for the complete checkpoint and any pack, keep cooling adequate, and monitor memory pressure, host writes, temperature and available drive-health counters. Measurements from the target NVMe drive are needed to turn this scenario into a useful endurance estimate.

Run InferSSD locally

Start with the installation guide. Both documented platforms use the main branch. Install Git, CMake, Ninja, a C/C++ compiler and Python 3.9 or later. macOS needs the Xcode command-line tools and Metal compiler. Linux needs a compatible CUDA toolkit, liburing development files and the documented systemd/cgroup memory controls.

Get the source
git clone --branch main https://github.com/wici-ai/inferssd.git
cd inferssd
python3 -m venv .venv
. .venv/bin/activate
python3 -m pip install ./framework

Build the backend and hardware probes for your platform, generate engine-resources.json, and copy the corresponding example runtime policy. Set its memory budget, host reserve and runtime limit for your machine. Download the model separately and keep every GGUF shard together; the launcher reads local files.

Launch with your local checkpoint
inferssd launch --execute \
  --resources engine-resources.json \
  --model /path/to/model-00001-of-00010.gguf --profile dsv \
  --runtime-policy runtime-policy.json

Replace the model path with the first shard. Muse uses --profile muse and the bundled Muse chat template. The first launch profiles the machine and model drive, which the guide says takes one to three minutes. Subsequent launches reuse the saved profile. Once the server is ready, open http://127.0.0.1:8080 or connect an OpenAI-compatible client to http://127.0.0.1:8080/v1.

The platform build commands and a streaming API example are also on the WiCi Infer page.

Source code and contributions

InferSSD is available under Apache-2.0. It builds on the work of llama.cpp, ggml and the model-adaptation community. Bundled components retain their original licenses and notices; model weights remain subject to their publishers’ licenses.

Useful contributions include improving overlap between reads and computation, cache policy and batching, exploring routed-expert execution on Metal, and measuring more CPUs, GPUs and SSDs. The current macOS path already has persistent readers and direct GGUF indexing; further work should build on those implementations.

Matched benchmarks are another priority. A reproducible report includes the source revision, checkpoint and quantization, full hardware configuration, launch command, memory budgets, prompt tokens, template and cache state.

Record prefill duration, timestamps across all 256 output tokens and total request time, with model loading measured separately. Include repeated runs, individual artifacts and a correctness check. Report unsupported models, failures and timeouts separately from completed measurements.

Get the source, follow the measurement checklist, or bring a result to GitHub Issues.
