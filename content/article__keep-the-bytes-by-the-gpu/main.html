TL;DR

  • A PCIe 5.0 x16 link can carry roughly 500 Gb/s in one direction; a practical Wi-Fi path is often gigabit-class. A local device transaction lives near the microsecond scale; a wireless round trip lives near the millisecond scale. Forwarding every byte and every call cannot preserve local-GPU behavior.
  • Keep reusable state on the GPU side. Active data stays in VRAM, warm state can sit in RAM, and a multi-terabyte SSD backs model weights that would otherwise cross Wi-Fi again. When one GPU call feeds another, pass a logical reference instead of returning a large intermediate to the client and uploading it again.
  • Saving bytes addresses bandwidth. Caching stable answers, batching independent calls, and replaying validated call patterns address round trips. Real dependencies and client-visible results still have to cross the boundary correctly.

The link is the scarce resource

The application, files, sensors, and interface remain on the client device. The nearby box executes GPU work while the app keeps using its normal graphics or compute interface. That is different from moving the whole application to a remote desktop. It also means a software boundary designed around a local bus now crosses Wi-Fi.

Local GPU software can ask many small questions and move large objects over PCIe inside the computer. Over Wi-Fi, both the data and the waiting become visible. The first useful question is what can stay on the GPU side after it arrives.

The bus ceiling is not the amount an application actually uses. In our 1080p Cyberpunk 2077 measurements, native host-to-GPU traffic averaged 7.88 Gb/s while rasterizing and 10.44 Gb/s with path tracing, with upscaling and frame generation disabled. A separate Wi-Fi 6 measurement reached 1.685 Gb/s of TCP uplink under favorable line-of-sight conditions. That puts this workload's native traffic about 4.7–6.2 times above that wireless baseline. They are different test setups, but the comparison shows the actual byte reduction the protocol has to pursue.

Remote time ≈ GPU work + bytes ÷ wireless goodput + blocking calls × RTT Keeping data nearby shrinks the middle term. Removing unnecessary waits shrinks the last one.

The last term can dominate even when the byte count is low. If every driver call waits for a wireless reply, the app spends time idle while the GPU is ready. Calls that only enqueue work can proceed without waiting; a true readback or fence still has to preserve its dependency.

Let the result stay where the next call needs it

Consider two GPU operations in sequence. The first produces a large tensor. The next uses that tensor as an input. If an interface copies the tensor back to the client's RAM and then uploads it for the next operation, the same bytes cross Wi-Fi twice. The client never needed to read them.

GPU APIs already have a useful idea for this: a device pointer or handle names data without containing the data. A wireless GPU runtime has to preserve that identity across machines. The client can hold a logical reference; the GPU box resolves it to an allocation and keeps the bytes in VRAM while they are active. Host RAM can hold selected evicted state; WiCi's SSD path currently centers on model weights. Extending that path to arbitrary GPU results is a separate research problem.

This is more precise than saying we “send a pointer.” A raw address from one process is not a valid address in another machine. The protocol needs a stable mapping from an app-visible reference to the right remote object, with ownership, lifetime, and synchronization preserved. If the CPU actually inspects the tensor, or the app needs a frame for display, those bytes must travel back.

Why put 4 TB beside the GPU?

A short-lived intermediate should stay in VRAM if possible. It does not need a 4 TB SSD. The drive matters for the larger, longer-lived working set: model weights too large for VRAM, or models repeatedly used by different sessions. Four terabytes is a capacity choice that lets the box retain much more of that working set locally instead of fetching it over Wi-Fi again.

A cache needs a way to recognize a hit. In our inference prototype, the client identifies a model tensor by its content and asks the box whether that tensor is already stored there. On a hit, the identity crosses Wi-Fi; on a miss, the bytes cross once and populate the cache. Identifying tiny objects can cost more than sending them, so the decision has to account for object size and reuse.

VRAM · hotActive tensors and kernels' working data. Fastest, smallest tier.
RAM · warmState worth restoring quickly when the active set changes.
SSD · deepModel weights that would otherwise be fetched again across Wi-Fi.

The drive is a backing store, not VRAM with a larger capacity label. Restoring weights still moves bytes from SSD toward GPU memory on the box's local PCIe path, sometimes through system RAM depending on the machine and software. The win is that a warm object need not be fetched again over Wi-Fi. Placement, prefetching, eviction, and the real local I/O path determine whether the result feels fast.

There is also a boundary on the cache's usefulness. A live camera frame that has never reached the box cannot be served from its SSD. A rendered frame the client must display cannot remain there forever. The cache helps when data is reused, or when a computation chain can keep its intermediate values near the GPU.

Wi-Fi bytes = new inputs + cache misses + client-visible outputs + changed client state Control messages still cross the link. SSD and GPU memory traffic remain real local costs.

Predict the calls, then verify

Saving bytes does not save the time spent waiting for thousands of small calls. GPU programs often repeat a pattern: allocate, load, launch, synchronize; an LLM decoding the next token may walk much the same call sequence as it did for the previous one. This is where the analogy to branch prediction becomes useful.

A CPU predicts which instruction path comes next so it can keep work moving. A wireless GPU runtime can recognize a known sequence, prepare data before the call arrives, combine compatible calls, or replay a validated trace on the box. When a later call uses an object created by an earlier one, a logical handle can let the client continue while the box resolves the real object. A prediction is useful only if the runtime checks it before the app can observe a wrong answer.

Patterned call batching and trace replay can reduce repeated inference traffic. Extending that idea to general driver calls is a harder research problem: allocations can fail, branches can change, and some effects cannot be rolled back. The safe design predicts where it has evidence, validates at synchronization points, and falls back to ordinary execution when the pattern breaks.

The measurement that matters

The right score is not the size of the SSD or the radio's advertised link rate. For each workload, measure how many bytes cross Wi-Fi after warm-up, what fraction of large objects hit the box-side cache, how often a call must block, how much SSD data is restored to VRAM, and what happens at the tail when the cache misses or another device competes for the GPU.

A useful comparison needs a cold run, a warm run, and a run that forces a host-visible readback. It must check output correctness as well as time. If the workload produces new data continuously or requires every intermediate on the client, a large cache cannot erase the link. If its working set is reused and its GPU results feed more GPU work, the wireless link can carry references and small changes while the box does the heavy movement locally.

That is the architectural bet behind putting substantial storage beside a nearby GPU: use capacity and knowledge of the computation to buy back the bandwidth Wi-Fi cannot provide.
