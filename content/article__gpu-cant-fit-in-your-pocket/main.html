Move the GPU Out. Keep It Local.

The mobile device is where the camera, microphone, files, display, sensors, and user interaction live. But it cannot carry the power and weight of the best GPU — so the GPU has to move out, nearby.

TL;DR

  • Personal AI needs real GPU headroom for interaction, memory, and adaptation — that need does not shrink; it is structural.
  • The mobile device has to remain the center of the experience because the camera, microphone, files, display, sensors, and user interaction live there.
  • The best GPU cannot live inside that device because its power and weight make it nearby infrastructure, not handheld hardware.
  • So the GPU has to move nearby — and a nearby GPU box only works if existing applications still behave as if the GPU is local; a new remote API is not enough.
The GPU can leave the device only if the device still feels like the computer in charge.

We laid out the case for that GPU headroom in The General and the Particular: interaction, memory, and adaptation are three GPU-accelerated loops a foundation model alone cannot cover, and each one gets better with more local compute, not less. That raises the obvious next question — if personal AI genuinely needs a powerful GPU, why not simply put one in the phone?

The experience starts on the mobile device

The phone, tablet, headset, or small robot is not just a screen attached to compute. It owns the camera, microphone, files, display, touch, sensors, identity, network context, and physical position of the user. For personal AI and interactive graphics, those are not peripherals. They are the workload's source of truth.

This is the result of a long shift in personal computing. The center of work used to be the desk: a workstation, a monitor, a keyboard, and files stored on the machine beside you. Then the workstation became portable. Then the pocket device became the camera, sensor hub, identity key, and always-present interface. Today the user-facing computer is often the device that moves with the person, not the box with the largest accelerator.

In GPU systems, the "host" is the computer that runs the application and coordinates the accelerator. It submits work, manages memory, receives results, and connects the output back to the user. In our system, that role has to remain with the mobile device, because that is where the user's world enters the system and where the result has to appear.

If that device becomes a thin client, the system inherits the old cloud problem in a smaller radius. A voice agent waits before responding. A camera pipeline waits before understanding the scene. A game waits before showing the next frame. A robot waits before acting. The distance may be across the room instead of across the country, but the user still experiences it as delay.

The target is therefore stronger than "phone calls GPU." The mobile device should still discover capability, submit work, receive frames, use local sensors, and run existing applications without a new per-app endpoint. The GPU can move, but the interaction loop must stay attached to the device in the user's hand.

The best GPU cannot fit inside it

The reason the GPU moves is physical. A top-end RTX 5090-class GPU draws 575 W, large boards can be about 358 mm long, and one retail model is listed at 6.64 lb, about 3.0 kg. That is not a mobile component. It is something that needs power delivery, cooling volume, and mechanical support.

For comparison, an iPhone 16 Pro Max is 227 g. The GPU board alone can weigh more than 13 of them. The point is not the exact model; it is the class of hardware. The best GPU belongs near the mobile device, not inside it.

Mobile GPUs exist, but they prove the same constraint. NVIDIA's RTX 5090 Laptop GPU is specified at 95-150 W of GPU subsystem power with 24 GB of GDDR7. The RTX 5090-class GPU at the top of the stack is a 575 W, 32 GB card. The laptop part becomes mobile by accepting a lower power and memory envelope; it is not the full object squeezed into a phone.

At the frontier, more capability is still bought with more power delivery, more memory, larger cooling, and heavier mechanical design. The mobile device cannot simply wait for the same GPU to become pocket-sized. The user-facing device stays mobile; the accelerator becomes infrastructure.

The GPU has to move nearby

Once the GPU cannot live inside the mobile device, the design space narrows quickly. Cloud GPUs offer scale, but they move the interaction loop across the internet and place every frame, sensor update, and user action behind a wide-area service boundary. Putting a high-end GPU into every device is physically and economically wrong. A nearby box is the remaining point: close enough for interactive use, stationary enough for wall power and cooling, and shared enough to justify the hardware.

This is why the nearby GPU box is not a product flourish. It is the architectural compromise forced by two facts: the user loop must stay mobile, and the frontier GPU has become stationary. The problem is that moving the GPU out of the chassis also moves the interconnect out of the chassis.

The architecture is forced: mobile device in charge, nearby accelerator, local feeling.

Nearby still has to feel local

A nearby box that exposes only a high-level API is still a remote service. It may work for a chat endpoint, an image endpoint, or a hand-written inference path, but it does not make the mobile device GPU-local. It asks every application to learn a new compute paradigm and only supports the tasks that endpoint designers predicted.

The existing GPU ecosystem is not organized around any API we could invent. Steam games target Direct3D, Vulkan, and driver-visible adapters. Video tools target encoders and graphics APIs. AI runtimes target CUDA, cuDNN, tensor libraries, and memory allocators. Blender, Unity, Unreal, PyTorch, and camera pipelines assume the accelerator appears through the normal device stack.

That is why the GPU has to feel local, and why that is much harder than it sounds: the mobile device now has to behave like a PCIe-attached host while the only practical link to the box is Wi-Fi — a network built for packets, not for the fine-grained, latency-sensitive chatter a local driver was designed to hide. We cover that boundary, what breaks when you try the obvious fixes, and how WiCi's protocol closes the gap, in Making a Nearby GPU Feel Local.

If every application needs a special remote-GPU path, the system has already failed as a local GPU.
