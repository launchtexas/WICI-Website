OpenAI just released GPT Live, but we can do better.

We ran the same spoken trivia against WiCi hold-to-talk Q&A and ChatGPT Live. The clip is short: local answers mid-question while Live is still listening.

Conversational speed is not commit-time latency

Interruptible chat still waits. Mid-question answers do not.

GPT Live is built for snappy dialogue: interruptible, smooth, “fast” in the chat sense. The demo still shows a gap that product copy does not name: when does the system decide it already knows enough to speak? One stack prints an answer while the other is still in a listening state on the same audio. That is not a model-quality contest; it is a race on the full audio path.

A typical voice pipeline is a relay: stream audio → ASR → wait for silence or end of turn → run the model → speak. Each hop looks fine alone. Stacked end-to-end, especially with cloud round-trips, the user feels the pause after they stop talking, or watches the remote UI sit in “listening” while a local system has already committed. Interruptible chat helps the conversation feel alive; it does not by itself give you mid-question answers.

Quiz-style buzzing makes that gap measurable. You are rewarded for answering before the question ends and punished if you are wrong. So the real product problem is three jobs at once: hear early, form an answer on a partial transcript, and only then decide that speaking is worth the risk. Knowing the answer is not the same as knowing when to speak. Latency lives in that gap.

The bottleneck is not “a smarter LLM.” It is an online loop that can think while the question is still being spoken, safely.

Why local makes this easier

This is the claim. Design details follow.

Voice latency is a stack: ASR, answerer, and the decision to speak. Cloud Live still pays RTT on every hop and tends to wait for enough of a turn before committing. Move the race to a nearby GPU and three things change at once:

  • No cloud round-trip between mic chunks, model, and buzz: the path is short enough to think while the question is still being spoken.
  • Audio stays on-device. Privacy is a product property, not an afterthought bolted onto a remote session.
  • You can afford online policies. Stream ASR, re-predict every few hundred milliseconds, and run a cheap gate on every candidate, all without shipping that loop through the public internet.

GPT Live proves the market wants conversational speed. Local compute is how you turn “interruptible chat” into “answer before they finish asking.” We can push the demo further (faster ASR, safer early buzzes); the reason it works at all is that the stack is local.

What has to be true for early answers

Reducing audio latency is three jobs: hear early, answer early, speak only when stable. The ceiling is simple: does the model ever become correct before the question ends?

On 1024 QANTA prefixes, answerability rises from ~81% at 4B to ~96% around 27–31B, and larger models get there earlier. If the model never knows mid-question, no gate invents an early right answer. Pick a model that can know early; then teach the system when to spend that knowledge.

How the online loop works

Hold to listen: ASR streams (~500 ms chunks). After enough prefix, the answerer predicts a short canonical answer. A separate BuzzGate scores only online-visible features (repetition, length, copy-from-transcript, dangling ASR, latencies; never gold or the future) and fires when score + repetition clear the bar.

Separate “what is the answer?” from “is it time?”

Do not ask one LLM to both answer and decide when to WAIT. That entangles accuracy and risk. Hand rules are brittle. We keep the answerer on the entity and train a small HGB BuzzGate on the timing side: strong repeated answers fire immediately; weaker ones need more evidence.

Median buzz around halfway through the question. The product claim is not a human quiz leaderboard. It is that answer generation and speak-timing can be split, and the timing layer can fire mid-sentence.

The remaining bottleneck is still audio

In the live path, ASR (~500 ms cadence) and the answerer (~140 ms) dominate; the gate is essentially free (~0.02 ms). Wrong early answers usually come from ASR (entity drops, year confusions), not from a slow gate. Speeding audio models means better streaming ASR and tighter local answerer kernels, with a gate that refuses flaky transcripts.

Answering is model capability. Buzzing is systems work. Local is what makes both cheap enough to run in the open.
